# Mission Reflection

A container is never truly isolated from the host beneath it — it shares that machine's CPU, memory, and disk. A container can appear perfectly healthy in `docker ps` while the host is running out of disk space, swapping heavily, or approaching a memory limit that will trigger the OOM killer. In this laboratory, the host had only 1.9GiB of RAM and a 19G root filesystem, hard limits that every container on the machine must share, so checking `free -h`, `df -h`, and `top` established what normal looked like before any load was applied. Without that baseline, a disk-full failure looks identical to a bug in the application, and I would have no way to tell whether the problem was inside the workload or underneath it.

Logs turn vague complaints into specific diagnoses. If a user reports they cannot log in, `docker logs` shows the chronological record of every request the container handled, including the status code returned: a 401 or 403 points to authentication logic, a 500 to a server-side exception, a 404 to a wrong or missing endpoint, and no entry at all suggests a networking or proxy issue upstream. In this lab the log line for `/hidden-admin-page` returned `404 153`, and the accompanying `[error]` entry explained the cause directly — `open() ".../hidden-admin-page" failed (2: No such file or directory)`. That combination of request line plus error line is exactly what converts a user complaint into an actionable finding.

Logs and metrics answer different questions. Logs are discrete, timestamped event records that explain *what happened and why*; metrics are numeric measurements over time that show *how much resource is being consumed right now*. Here, `docker logs` revealed that a 404 occurred and why, while `docker stats` revealed the container was using 2.746MiB of memory and 0.00% CPU. Logs diagnose a specific failure; metrics detect trends, capacity problems, and performance degradation before they become failures — and effective operations needs both.

Manual commands do not scale to thousands of containers, so enterprises centralize observability. Metrics are scraped from every host and container by tools such as Prometheus, stored in a time-series database, visualized in Grafana dashboards, and paired with alerting rules that page an on-call engineer when thresholds are crossed. Logs are shipped to a centralized aggregator such as Loki, the ELK stack, or a cloud logging service so they can be searched across the entire fleet instead of one container at a time, with Kubernetes adding orchestration and health checks on top. The principle from this lab still holds — logs explain events, metrics measure resources — but at scale those signals are collected, correlated, and alerted on automatically rather than read by hand.

My troubleshooting has become more deliberate as a result. I now establish a baseline before changing anything, read raw command output instead of relying on summaries, and separate host-level symptoms from container-level ones. I can confirm a deployment actually succeeded with `docker ps`, and trace a user-visible error from its HTTP status code back to the underlying filesystem error in the logs. That structure — check the foundation, then the workload, then the evidence — is a repeatable method I can apply to unfamiliar Linux systems, not just this one scenario.
