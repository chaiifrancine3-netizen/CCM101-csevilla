# Multi-Tier Architecture

## What is a Two-Tier Architecture?

A **two-tier architecture** (also called *client–server architecture*) is a
software design in which a system is organized into exactly two logical
layers: a **Web/Application tier** that handles user interaction and request
processing, and a **Database tier** that stores and manages persistent data.
The client (the user's browser) communicates only with the web tier, and the
web tier is the only component that talks to the database.

In this laboratory, the two tiers are deployed as **two separate Docker
containers** orchestrated by Docker Compose, so each tier runs as an isolated
service with its own image, configuration, and lifecycle.

---

## The Web/Application Tier

**Role:** Serving the user interface and handling HTTP requests.

- Acts as the **entry point** for all client traffic (typically on port 80/443).
- Serves **static assets** (HTML, CSS, JS, images) and/or renders **dynamic
  pages** generated by server-side code.
- Executes **business logic** — authentication, validation, session handling,
  and orchestration of data queries.
- Translates client requests into **database queries**, and formats the
  database response back into HTML/JSON for the client.
- In this lab, this tier is the container built from our web application image
  (e.g., a PHP/Apache or Node.js service defined in `docker-compose.yml`).

---

## The Database Tier

**Role:** Storing persistent data, user accounts, and application state.

- Persists **structured data** in tables — users, credentials, orders,
  configuration, logs, etc.
- Enforces **data integrity** through schemas, primary/foreign keys,
  constraints, and transactions.
- Provides **concurrent access** to many web-tier requests safely.
- Handles **backup, indexing, and query optimization**.
- In this lab, this tier is a database container (e.g., MySQL, MariaDB, or
  PostgreSQL) with a **named volume** so data survives container restarts.

---

## Why Separate the Two Tiers?

Keeping the web server and database in **two separate containers** instead of
packing them into one gives us **independent scaling** (we can run many web
containers behind a load balancer while keeping one database), **isolated
failure domains and security boundaries** (a compromised web container does
not automatically expose the data store, and the database is not reachable
from the public internet), and **simpler maintenance** (each tier can be
upgraded, rolled back, or replaced without touching the other). It also
enables **persistent data** to live in a dedicated volume that outlives web
container rebuilds, and lets each tier use the **runtime best suited to it**
(e.g., a PHP runtime for the web tier, a tuned MySQL server for the database).
