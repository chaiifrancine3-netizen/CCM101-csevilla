# Reflection

Writing a `docker-compose.yml` file makes a cloud engineer's job easier because it replaces a fragile, multi-step manual process with a single repeatable command. With `docker run`, I had to remember every flag — network creation, port mappings, environment variables, and correct start order — and retype them correctly each time; one typo and the app could not find the database. With a Compose file, all of that is declared once, version-controlled in Git, and reproducible on any machine by running `docker-compose up -d`, which is the difference between a recipe written from memory and a recipe written down. If I make an indentation error, such as using a Tab instead of Spaces, YAML fails fast: Docker Compose refuses to parse the file and throws an error like "found character '\t' that cannot start any token" or "did not find expected key", pointing to the offending line. Unlike a runtime bug, an indentation mistake does not partially work — the file simply will not load, which is actually helpful because it forces me to fix the problem before anything deploys, and `docker-compose config` lets me validate the syntax before touching a live stack. We used environment variables like `MYSQL_PASSWORD`, `MYSQL_DATABASE`, and `MYSQL_HOST` to separate configuration from code, so the same images work across development, staging, and production with only the injected values changing, and so the two containers can agree on credentials and connection details without hardcoding them into an image. It also keeps secrets out of the container itself, letting me rotate a password by editing one line — or better, an untracked `.env` file — instead of rebuilding anything. Deploying a fully functional enterprise cloud storage system in just a few minutes felt a little surreal, because Nextcloud is the kind of tool I would expect to take an afternoon of Apache configuration, PHP extensions, and database setup, yet `docker-compose up -d` pulled two images and, within a couple of minutes, I was staring at the real Nextcloud setup screen in my browser — the complexity was still there, just hidden behind a well-written blueprint. Since Mission 1, my understanding of cloud computing has evolved from thinking of it as "someone else's servers" to seeing it as composable infrastructure defined by code, where containers, service discovery, environment-based configuration, and declarative orchestration are the building blocks behind Kubernetes, ECS, and every major cloud platform — the shift from imperative commands to declarative files is the same shift the whole industry made, and this lab made that click for me.
